# Kitty 工作台账号登录与云同步设计

## 1. 目标

在不破坏已有本地记录和离线能力的前提下，为 Kitty 工作台增加公开邮箱注册、6 位邮箱验证码登录、跨设备云同步与首次本地数据迁移。

成功标准：

- 老用户更新应用后，无需登录即可继续访问原有本地记录。
- 手机与电脑登录同一账号后可同步全部工作台数据。
- 未经用户确认，不上传已有本地数据。
- 迁移、同步或网络失败时不清空本地记录。
- 每个账号只能访问自己的数据。
- 原有 Excel 导出、JSON 备份恢复和 PWA 离线能力继续可用。

## 2. 已批准的产品决策

- 只改 Kitty 粉色工作台，不修改浅蓝云朵熊工作台。
- 使用 Supabase Authentication 和 PostgreSQL。
- 允许任何人使用邮箱注册。
- 登录方式为邮箱 6 位数字验证码，不设置密码。
- 没有自有域名；开发阶段使用 Supabase 测试邮件，正式开放前配置自定义 SMTP。
- 支持离线记录，恢复联网后自动同步。
- 同一记录发生冲突时，以最后修改时间较新的版本为准。
- 首次登录发现本地记录时，必须由用户确认后再上传合并。
- 迁移成功前不删除本地数据；成功后仍保留本地缓存和 JSON 备份能力。

## 3. 用户体验

### 3.1 访客模式

工作台默认保持现有行为。未登录用户可创建、修改、删除、导出和恢复本地记录。设置页新增“登录并同步”入口，不以全屏登录页阻挡原有用户。

### 3.2 邮箱验证码登录

登录界面包含邮箱输入、发送验证码、6 位验证码输入、重新发送倒计时和返回本地模式。验证码发送后对邮箱地址做部分隐藏。认证错误使用中文提示，不泄露账号是否已存在。

Supabase 中启用 Email OTP，验证码有效期使用服务端配置。开发阶段测试邮件仅用于受限测试；正式公开注册是发布门禁，必须先接入自定义 SMTP 和发件域名。

### 3.3 首次登录迁移

登录成功后检测旧存储键 `kitty-workbench`。若存在本地记录，展示各模块数量：待办、记账、减脂、日程、纪念、日记、经期。

用户可选择：

- “确认上传并合并”：创建迁移批次，将本地数据转换为云端记录并上传。
- “暂不迁移”：保留本地原始数据，不自动上传；用户稍后可从设置页再次发起。

迁移规则：

- 每个迁移批次有唯一 `migration_id`。
- 本地记录生成稳定 UUID；重复执行同一批次使用 upsert，不产生重复记录。
- 云端已有记录时按记录 UUID 合并，不整包覆盖。
- 所有模块上传成功并完成数量校验后，才将批次标记为完成。
- 迁移失败显示失败模块和重试入口，不删除或改写旧本地备份。

### 3.4 登录后状态

设置页“账号与同步”卡片显示：脱敏邮箱、同步状态、最后同步时间、待同步条数、立即同步和退出登录。

状态包括：

- 所有数据已同步
- 离线使用中
- 有 N 条待同步
- 同步失败，可重试

退出登录只清理该账号的会话和账号缓存，不删除云端数据，也不删除迁移前的原始本地备份。

## 4. 数据模型

### 4.1 表结构

使用一个统一的 `workbench_records` 表，避免为七个模块重复维护同步逻辑：

- `id uuid`：记录唯一标识。
- `user_id uuid`：所属用户，引用认证用户。
- `record_type text`：`task`、`account`、`fitness`、`event`、`keepsake`、`diary`、`cycle`、`profile`。
- `payload jsonb`：原模块记录内容。
- `created_at timestamptz`：创建时间。
- `updated_at timestamptz`：最后修改时间。
- `deleted_at timestamptz null`：软删除时间。
- `migration_id uuid null`：首次迁移批次。
- `device_id text`：最后写入设备标识，用于诊断同步问题。

唯一键为 `(user_id, id)`。为 `(user_id, record_type, updated_at)` 建索引。

`migration_batches` 表记录迁移进度：`id`、`user_id`、`device_id`、模块数量、状态、错误摘要、创建与完成时间。

### 4.2 权限

两张表均启用 Row Level Security。读取、新增、修改和软删除策略均要求 `auth.uid() = user_id`。浏览器只使用 Supabase anon key；service role key 不进入前端、仓库或构建产物。

## 5. 本地缓存与同步

### 5.1 存储隔离

- `kitty-workbench`：保留为升级前的原始本地数据和访客模式数据。
- 登录账号缓存使用按用户隔离的 IndexedDB 空间，键包含用户 ID。
- 设备生成稳定 `device_id`，不包含硬件指纹或个人信息。
- 切换账号前关闭当前同步队列，加载目标账号缓存，禁止跨账号合并。

### 5.2 写入流程

用户操作先写入本地缓存并立即更新界面，再将变更加入同步队列。在线时后台批量 upsert；离线时队列保留。网络恢复、应用启动、登录完成和用户点击“立即同步”时触发同步。

删除写入 `deleted_at`，不立即物理删除。这样其他离线设备上传旧副本时不会恢复已删除数据。

### 5.3 冲突处理

每次同步先拉取服务端增量，再推送本地待同步项。对同一 UUID：

- `updated_at` 较晚者生效。
- 时间相同且内容不同，以服务端版本为准并记录诊断日志。
- 删除也是一个带时间戳的版本；较新的删除覆盖旧内容，较新的有效编辑可恢复旧删除。

客户端生成时间用于即时离线操作，服务端同时保存接收时间。若设备时钟偏差过大，显示同步异常提示，不静默覆盖大量记录。

## 6. 组件边界

- `AuthProvider`：维护 Supabase 会话和登录状态。
- `LoginDialog`：邮箱、验证码、重发和错误状态。
- `MigrationDialog`：本地统计、确认、进度、失败重试。
- `SyncProvider`：本地缓存、队列、网络监听、拉取和推送。
- `AccountSyncCard`：设置页账号与同步状态。
- `dataRepository`：为现有页面提供与当前 `data/setData` 等价的数据接口，避免业务组件直接依赖 Supabase。
- `supabaseClient`：只负责读取环境变量并创建客户端。

现有页面的业务交互保持不变；账号与同步逻辑不散落到待办、记账等页面。

## 7. 环境与部署

前端通过以下构建变量连接 Supabase：

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

本地使用未提交的 `.env.local`。GitHub Pages 构建从 GitHub Actions Secrets 注入。仓库提供 `.env.example`，不包含真实密钥。

需要创建 Supabase 项目、执行数据库迁移 SQL、启用 Email OTP，并将本地地址和 GitHub Pages 地址加入认证重定向白名单。没有可用 Supabase 项目和 anon key 时，应用继续以本地模式运行，并隐藏不可用的发送验证码动作，不能伪装成已配置成功。

## 8. 错误与安全

- 验证码发送设置冷却时间，防止连续请求。
- 登录、迁移和同步错误均提供重试，不清除输入或本地记录。
- 不在控制台记录验证码、完整邮箱、认证 token 或记录正文。
- 登出后移除会话 token；账号缓存按用户隔离。
- JSON 恢复到已登录账号时，先恢复至本地预览，用户再次确认后加入同步队列，不直接覆盖云端整包数据。
- 应用升级和 Service Worker 刷新不得在同步队列未持久化时触发数据丢失。

## 9. 验证与验收

### 自动验证

- 本地数据转换为 UUID 记录，重试迁移不重复。
- 按用户隔离缓存与查询。
- 最后修改时间冲突、软删除、离线队列重放。
- 无 Supabase 配置时安全降级到本地模式。
- 生产构建、依赖审计和静态检查通过。

### 浏览器验证

- 老版本 `kitty-workbench` 数据在升级后保持可见。
- 邮箱发送、6 位验证码登录、登出和会话恢复。
- 首次迁移在确认前不发起上传；取消后本地数据不变。
- 迁移中断后可重试且无重复记录。
- 两个浏览器会话模拟手机与电脑，验证新增、修改、删除和最后修改优先。
- 离线新增后恢复联网可同步。
- Excel 导出、JSON 备份恢复、PWA 更新提示无回退。
- 390×844 与桌面宽度无横向溢出，登录和迁移弹窗可键盘操作。

## 10. 实施边界

本次包含登录、迁移、同步、数据库迁移和部署配置，但不包含自定义域名、正式 SMTP、社交账号登录、管理员后台、共享账号或多人协作。正式向任何邮箱开放注册前，必须另行完成域名与 SMTP 配置并验证送达率。
